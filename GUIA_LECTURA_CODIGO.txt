GUÍA DE LECTURA DEL CÓDIGO — Gestión de Datos Personales
================================================================================

Propósito de este archivo: servir de recorrido instructivo desde el PRIMER archivo
que conviene abrir hasta entender el sistema completo. Está pensado para alguien
que sabe Programación Orientada a Objetos (clases, objetos, herencia, métodos)
pero nunca ha trabajado con FastAPI, SQLAlchemy, Docker, React ni n8n.

Regla de uso: no pases al paso siguiente hasta poder responder la pregunta que
abre el paso actual. Cada paso termina con una comprobación. Los términos nuevos
se explican la primera vez que aparecen y se comparan con conceptos de POO.

Ruta recomendada: 0 → 12 (unas 5–6 horas la primera vez). Para repasar, salta
directo al paso 3 (datos), 5 (auth) u 8 (CRUD).

================================================================================
0. GLOSARIO MÍNIMO (léelo antes de abrir archivos)
================================================================================

Microservicio     Una aplicación pequeña e independiente con una responsabilidad.
                  En POO sería una clase con un único propósito, desplegada en su
                  propio contenedor. Aquí cada opción del menú vive separada.

Gateway           "Fachada" del sistema: Nginx en el puerto 80. La SPA y n8n hablan
                  SOLO con él, nunca con un microservicio. En POO sería la clase
                  pública que esconde la complejidad de las clases internas.

Endpoint          Un método HTTP (GET/POST/PUT/DELETE) asociado a una URL.
                  GET /api/v1/query/123 es "llama al método consultar con 123".

Depends           Inyección de dependencias de FastAPI. En POO pasarías un
                  colaborador por el constructor; aquí el framework construye la
                  sesión de BD, el usuario o el token y se lo pasa ya listo al
                  endpoint. Por eso los parámetros llevan `= Depends(...)`.

APIRouter(prefix=) Un "controlador" que agrupa rutas bajo una URL base. Su prefijo
                  debe coincidir EXACTAMENTE con un `location` de nginx.conf.

Pydantic          Validación de datos en Python. Un `BaseModel` es como un objeto
                  con setters que validan: si el dato no cumple, lanza error y
                  FastAPI responde 422 sin entrar a tu función.

Zod               El equivalente en TypeScript/React. Define el mismo esquema en
                  el navegador para dar feedback antes de llamar al backend.

ORM (SQLAlchemy)  Traduce clases Python a tablas SQL. `Persona` es la clase, cada
                  instancia es una fila y `db.add(objeto)` prepara un INSERT.

Migración         Control de versiones de la BD con Alembic. Nunca se edita una
                  migración ya aplicada: se crea una nueva revisión.

JWT / Bearer      Un "pase" firmado. El login devuelve un token y la SPA lo envía
                  en la cabecera `Authorization: Bearer <token>`. Es como una
                  credencial de usuario que no requiere enviar la contraseña en
                  cada petición.

Embedding         Lista de 768 números que representa el SIGNIFICADO de un texto.
                  Textos parecidos producen vectores cercanos.

pgvector          Extensión de PostgreSQL que guarda vectores y busca por similitud
                  con distancia coseno (`<=>`) e índice HNSW.

RAG               Retrieval-Augmented Generation: buscar fragmentos parecidos a
                  la pregunta y dárselos al LLM para que responda con datos reales.
                  El chat vive en n8n, no en React.

Componente / hook Un componente es una "clase visual" reutilizable de React (una
                  función que devuelve JSX, similar a un `render()`). Un hook es
                  una función con estado interno, como un método que recuerda datos
                  entre renders (`useState`, `useAuth`, `useServicio`).

TanStack Query    Gestor de peticiones: guarda resultados en caché, reintenta y
                  permite recargar. En POO sería un objeto que administra llamadas
                  remotas y su estado (cargando / error / datos).

React Hook Form   Formularios: registra campos y valida con Zod antes de enviar.
                  `register("correo")` conecta el input con el estado del formulario.

Health check      Endpoint `/health` que responde `{"status":"ok"}`. Sirve para
                  decidir si un panel se muestra o se marca "servicio inactivo".

2. LA FACHADA: ¿CÓMO LLEGA UNA PETICIÓN AL CONTENEDOR CORRECTO?
================================================================================

Archivos:
  2.1  gateway/nginx.conf
  2.2  gateway/proxy.conf
  2.3  gateway/entrypoint.sh
  2.4  frontend/Dockerfile y frontend/nginx-spa.conf

Qué fijarse:
  - `upstream` define nombres lógicos (`ms_auth`, `ms_create`, …). Docker resuelve
    `ms-auth:8000` por DNS interno. En POO sería un mapa nombre → colaborador.
  - Cada `location /api/v1/...` apunta a un upstream distinto, SIN barra final.
    Si se pusiera `/api/v1/create/`, Nginx haría 301 y FastAPI devolvería 307 de
    vuelta: bucle de redirecciones.
  - `/n8n/` SÍ lleva barra final en `proxy_pass http://n8n_service/;`: así
    `/n8n/rest/...` llega como `/rest/...`. Sin ella, la API REST caía en el HTML
    del editor de n8n.
  - `resolver 127.0.0.11` es el DNS de Docker. Permite que Nginx arranque aunque
    `frontend` o `ms-person-query` no estén levantados (base de la prueba R7).
  - `location /api/v1/query` usa `proxy_pass` con variable y `error_page 502 503
    504 = @query_offline`: devuelve un 503 JSON controlado sin tumbar al resto.
  - `location /` usa la misma técnica con `@no_ui`: si no levantas el frontend,
    responde 200 con instrucciones en vez de un 502 feo.
  - SECURITY: `/n8n/` aplica basic-auth; el htpasswd se genera en `entrypoint.sh`
    desde `N8N_USER`/`N8N_PASSWORD`. `client_max_body_size 3m` deja subir una foto
    de hasta 2 MB más el overhead del formulario. `/n8n/` tiene 300 s de timeout
    de lectura porque el LLM local puede tardar; el resto, 60 s.
  - El contenedor `frontend` compila la SPA y su propio Nginx escucha en 5173;
    el gateway lo publica como `/`. Las variables `VITE_*` se sustituyen en BUILD
    (ARG del Dockerfile + build args de Compose), no en runtime.

Comprobación: explica en voz alta por qué `/api/v1/create` no tiene barra final
pero `/n8n/` sí, y qué ocurre si `ms-person-query` está detenido.

3. EL CONTRATO DE DATOS: ¿QUÉ REGLAS SE VALIDAN Y DÓNDE SE REPITEN?
================================================================================

Archivos (léeos en paralelo, uno al lado del otro):
  3.1  contexto.md §2.3 — reglas originales del enunciado.
  3.2  backend/shared/schemas.py — Pydantic v2 (autoridad).
  3.3  frontend/src/shared/lib/validation.ts — Zod (espejo).
  3.4  backend/tests/test_schemas.py (12 pruebas) y
       frontend/src/shared/lib/validation.test.ts (8 pruebas).

Mapa de una regla a su implementación:

  Regla del enunciado      Pydantic                         Zod
  -----------------------  -------------------------------  ----------------------------
  Tipo documento (2)       TipoDocumento(str, Enum)         z.enum(TIPOS_DOCUMENTO)
  Nro. documento ≤10       Field(min_length=1,             .min(1).max(10)
  y solo dígitos            max_length=10, pattern=…)       .regex(/^\d{1,10}$/)
  Nombre sin números       @field_validator → _sin_digitos  textoSinDigitos(...)
  Nombre ≤30 / apellido≤60 Field(max_length=…)              .max(30) / .max(60)
  Segundo nombre opcional  validator mode="before" → None   z.union([…, z.literal("")])
  Fecha dd-mmm-yyyy o ISO  _parse_fecha_nacimiento()        fechaValida() + MESES_ES
  Género (4 valores)       Genero(str, Enum)                z.enum(GENEROS)
  Correo válido            EmailStr                         .email()
  Celular exactamente 10   Field(pattern=r"^\d{10}$")       .regex(/^\d{10}$/)
  Foto ≤2 MB               foto_size + MAX_FOTO_BYTES       File.size + MAX_FOTO_BYTES
  Filtros de log           LogCreate/LogOut                 filtrosLogSchema (desde ≤ hasta)

Detalles que explican decisiones:
  - `mode="before"` en Pydantic se ejecuta antes de la validación de tipo: convierte
    el string vacío del formulario en `None` y la fecha en texto a objeto `date`.
  - Los meses son en español (`ene`, `feb`, …) por decisión del equipo; el datepicker
    envía ISO `YYYY-MM-DD` y ambos formatos se aceptan en los dos lenguajes.
  - En Zod, `refine` devuelve un `ZodEffects` que ya no admite `.min()`/`.max()`;
    por eso `textoSinDigitos` aplica longitud ANTES y el refine de dígitos al final.
  - `TipoTransaccion` / `TIPOS_TRANSACCION` deben coincidir: CREATE, READ, UPDATE,
    DELETE, RAG_QUERY.

Comprobación: cambia mentalmente el celular a 12 dígitos. Deberías saber que hay
que tocar cuatro sitios: contexto §2.3, schemas.py, validation.ts y ambas suites
de pruebas. La rúbrica R5 (4 pts) exige que estén en frontend Y backend.

5. AUTENTICACIÓN: ¿CÓMO SE CONVIERTE UN LOGIN EN UNA PETICIÓN PROTEGIDA?
================================================================================

Archivos en orden:
  5.1  backend/ms-auth/app/main.py       — rutas /signup, /login, /verify-token,
                                          /service-token, /logout, /health.
  5.2  backend/ms-auth/app/roble_client.py — mock vs SDK ROBLE, firma JWT HS256.
  5.3  backend/shared/roble_storage.py    — excepción síncrona del SDK.
  5.4  backend/shared/security.py         — get_current_user y get_access_token.
  5.5  frontend/src/shared/lib/auth-context.tsx — sesión en sessionStorage.
  5.6  frontend/src/features/auth/login-page.tsx — formulario público.
  5.7  frontend/src/shared/lib/api.ts (líneas 66–105) — Bearer y evento 401.

Flujo:
  SPA /login ──POST /api/v1/auth/login──▶ ms-auth
      AUTH_MODE=mock  → usuario fijo, contraseña ignorada, JWT HS256 de 7 días
      AUTH_MODE=roble → SDK oficial + sesión persistida en roble_token_storage
                     ◀── {access_token, user}
  SPA guarda `gd_sesion` en sessionStorage (NO localStorage: muere al cerrar pestaña)
  SPA ──Authorization: Bearer <token>──▶ gateway ──▶ microservicio
      Depends(get_current_user) ──GET ms-auth/api/v1/auth/verify-token──▶
          200 → current_user / 401 → "Token inválido" / error de red → 503

Detalles que explican decisiones:
  - SECURITY: los microservicios NO decodifican el JWT por su cuenta; le preguntan
    a ms-auth. Así un logout en ROBLE invalida el token aunque la firma siga viva.
  - `get_access_token` entrega el token crudo para reenviarlo a ms-logs por HTTP.
  - `POST /service-token` con cabecera `X-Service-Key` es la excepción controlada:
    lo usa n8n para registrar RAG_QUERY sin credenciales de usuario.
  - SECURITY: JWT_SECRET_KEY y ROBLE_CONTRACT_ID solo viven en el entorno; si falta
    el secreto, `roble_client.py` falla al importar (fail fast).
  - `api.ts` lanza el evento global `gd:unauthorized` cuando ve un 401;
    `auth-context.tsx` lo escucha, borra `gd_sesion` y devuelve al usuario al login.

Comprobación: ¿por qué un 503 en ms-auth no debe confundirse con un 401? Porque
503 significa "autoridad caída" y 401 "credencial inválida"; el código los distingue.

6. COLABORADORES TRANSVERSALES: ¿CÓMO SE REGISTRA, SE INDEXA Y SE GUARDA UNA FOTO?
================================================================================

Archivos:
  6.1  backend/shared/log_client.py
  6.2  backend/shared/embedding_client.py
  6.3  backend/shared/uploads.py

Qué fijarse:
  - `registrar_transaccion()` es un adapter HTTP a ms-logs: el microservicio no
    escribe en `transaccion_logs` directamente. Reenvía el Bearer y lanza error si
    ms-logs responde ≥400. Por eso los endpoints hacen `flush` → log → `commit`:
    si el log falla, `rollback` y el usuario recibe 503. Nunca queda una operación
    sin auditoría (rúbrica R2, 15 pts).
  - `generar_embedding()` llama a Ollama `/v1/embeddings` con `nomic-embed-text`,
    fuerza 768 dimensiones y verifica la longitud del vector. Es mejor esfuerzo:
    create/update solo avisan por `logger.warning` si falla; la persona ya quedó
    guardada y el CRUD responde 201.
  - `texto_para_embedding()` incluye nombre, documento, fecha de nacimiento y
    género con prefijo `search_document:`. La fecha es lo que permite responder
    "¿quién es el más joven?" (riesgo #1 del contexto).
  - `guardar_foto()` escribe en el volumen compartido `uploads_data` con un UUID
    para evitar sobrescrituras; devuelve `/uploads/<uuid>.<ext>`, que Nginx sirve
    en solo lectura. El límite de 2 MB se valida en Pydantic y en Zod.

Comprobación: ¿qué diferencia hay entre que falle ms-logs y que falle Ollama?
El primero revierte la operación; el segundo solo degrada la búsqueda semántica.

8. CRUD: ¿CÓMO SE IMPLEMENTA CADA OPCIÓN DEL MENÚ?
================================================================================

Léelos en este orden (de más simple a más completo):

  Paso 8.1  backend/ms-person-query/app/main.py

  Paso 8.2  backend/ms-person-delete/app/main.py

  Paso 8.4  backend/ms-person-update/app/main.py
            Igual que create pero PUT /{documento}. Verifica que la ruta y el
            formulario tengan el MISMO documento (422 si no), usa `setattr` sobre
            el objeto ORM, log UPDATE, commit, borra el vector viejo y crea uno
            nuevo (reindexado), `db.refresh()` antes de responder.
            frontend/.../actualizar-page.tsx reutiliza el modal de alta.

Componentes frontend que evitan repetir código:
  - buscar-documento-form.tsx: un solo formulario Zod para los tres paneles que

  - use-consulta-persona.ts: hook con `{persona, error, buscando, buscar, limpiar}`.
  - lista-tarjetas.tsx: presenta personas y logs con el mismo estilo de cards.
  - format.ts: fechas legibles y mensajes de error de ApiError.

Códigos HTTP que conviene memorizar:
  200 operación correcta · 201 creado · 204 borrado sin cuerpo · 401 token inválido
  · 404 persona no encontrada · 409 documento duplicado · 422 validación
  · 503 servicio dependiente caído (auth o logs).

Comprobación: tracea mentalmente un CREATE desde que el usuario pulsa "Crear

9. RAG: ¿CÓMO SE RESPONDE EN LENGUAJE NATURAL SIN REIMPLEMENTAR EL CHAT?
================================================================================

Archivos:
  9.1  backend/shared/embedding_client.py (ya leído en el paso 6)
  9.2  n8n/workflows/rag_consulta_personas.json
  9.3  backend/ms-auth/app/main.py (`/service-token`)
  9.4  backend/ms-logs/app/main.py (`POST /api/v1/logs`)
  9.5  frontend/src/features/rag/rag-page.tsx
  9.6  gateway/nginx.conf (`/n8n/`)
  9.7  contexto.md §6 y riesgo #1 en §8

El JSON de n8n NO admite comentarios: la tabla `connections` define el orden.
Los 11 nodos, en orden real:

  1. Chat Trigger        → pregunta del usuario en el widget de n8n.
  2. Embed pregunta      → Ollama `/v1/embeddings`, prefijo `search_query:`.
  3. SQL vectorial       → arma el literal del vector y la SQL con similitud
                           `1 - (pe.embedding <=> '<vector>'::vector)` LIMIT 5.
  4. Buscar similares    → ejecuta la SQL con la credencial Postgres.
  5. Agregados           → consulta máximo/mínimo por `fecha_nacimiento`.
  6. Armar contexto      → quita `similitud`, compone `nombre_mas_joven` y entrega
                           `{pregunta, contexto}`; recupera la pregunta con
                           `$('Chat Trigger').first().json.chatInput`.
  7. LLM Ollama          → `qwen2.5:0.5b`, temperature 0, español, solo contexto.
  8. Preparar respuesta  → extrae `choices[0].message.content` en `texto`.
  9. Token de servicio   → `X-Service-Key` → JWT de ms-auth.
 10. Registrar RAG_QUERY → POST ms-logs con `{pregunta, respuesta}`.
 11. Respuesta al chat   → copia `texto` al campo `text` que espera el widget.

Detalles que explican decisiones:
  - La pregunta oficial es *"¿Cuál es el empleado más joven que se ha registrado?"*.
    El texto indexado incluye la fecha y el nodo `Agregados` hace SQL adicional,
    porque un embedding por sí solo no garantiza un min/max exacto.
  - SECURITY: n8n no expone el puerto 5678; entra por `/n8n/` con basic-auth del
    gateway. $env.OLLAMA_* se lee porque `N8N_BLOCK_ENV_ACCESS_IN_NODE=false`.
  - El panel React `/rag` SOLO comprueba `/n8n/healthz` y abre el webhook real
    `/n8n/webhook/chat-rag-consulta-personas/chat` en otra pestaña. Un 401 del
    basic-auth cuenta como "gateway vivo"; un 502/503 como "servicio inactivo".
    La conversación se ve en n8n porque la rúbrica R3 (12 pts) lo exige.

Comprobación: explica por qué el chat NO está en React y dónde queda registrada
cada pregunta.
