================================================================================
GUÍA DE LECTURA DEL CÓDIGO — Gestión de Datos Personales
================================================================================

Público objetivo: alguien que entiende Programación Orientada a Objetos (clases,
objetos, herencia, métodos) pero NUNCA ha trabajado con FastAPI, SQLAlchemy,
Docker ni n8n. Los comentarios del código están escritos con ese mismo criterio:
explican el PORQUÉ de cada decisión y traducen los conceptos nuevos a analogías
de POO. No es necesario leerlo todo de una vez: sigue el orden de esta guía.


--------------------------------------------------------------------------------
1. GLOSARIO MÍNIMO (léelo antes de abrir archivos)
--------------------------------------------------------------------------------

Microservicio      Una aplicación pequeña e independiente con una responsabilidad.
                   Aquí cada opción del menú es un contenedor distinto (rúbrica).
Gateway            "Fachada": único punto de entrada (Nginx, puerto 80). La SPA
                   y n8n llaman SOLO al gateway, nunca a un microservicio.
Endpoint           Un método HTTP (GET/POST/PUT/DELETE) asociado a una URL.
Depends            Inyección de dependencias de FastAPI. En POO pasarías un
                   colaborador por el constructor; aquí el framework construye
                   el objeto (sesión de BD, usuario, token) y se lo pasa ya listo
                   a la función. Por eso los parámetros tienen `= Depends(...)`.
APIRouter(prefix=) Un "controlador" que agrupa rutas bajo una URL base. El
                   prefijo debe coincidir EXACTAMENTE con gateway/nginx.conf.
Pydantic           Librería de validación. Un `BaseModel` es como un objeto con
                   setters que validan: si el dato no cumple, lanza error y
                   FastAPI responde 422 sin entrar a tu código.
async / await      Programación asíncrona. Mientras se espera la base de datos o
                   una API externa, el servidor atiende otras peticiones. En POO
                   sería como no quedarse bloqueado esperando a un colaborador.
ORM (SQLAlchemy)   Traduce clases Python a tablas SQL. `Persona` es una clase;
                   cada instancia es una fila; `db.add()` prepara el INSERT.
Migración          Control de versiones de la BD (Alembic). Nunca se edita una
                   migración ya aplicada: se crea una nueva con `revision`.
JWT / Bearer       Un "pase" firmado. El login devuelve un token; el frontend lo
                   envía en la cabecera `Authorization: Bearer <token>`. Todos
                   los endpoints protegidos lo verifican con get_current_user.
Embedding          Lista de números que representa el SIGNIFICADO de un texto.
                   Textos parecidos -> vectores cercanos. 768 números aquí.
pgvector           Extensión de Postgres que guarda vectores y permite buscar
                   por similitud (distancia coseno) con el índice HNSW.
RAG                retrieval-augmented generation: buscar fragmentos parecidos
                   a la pregunta y dárselos al LLM para que responda con datos
                   reales en vez de inventarlos. El chat vive en n8n.

3. FLUJO DE UNA PETICIÓN REAL (ejemplo: crear persona)
--------------------------------------------------------------------------------

  1. La SPA envía POST /api/v1/create con multipart/form-data y el Bearer.
  2. Nginx (`location /api/v1/create`) la pasa a ms-person-create:8000.
  3. FastAPI valida campos con Pydantic (422 si falla) e inyecta por `Depends`:
     la sesión `get_db`, el `current_user` verificado y el token crudo.
  4. `shared.security.get_current_user` llama a ms-auth/api/v1/auth/verify-token.
     Si ms-auth está caído -> 503; si el token es malo -> 401.
  5. El endpoint construye `PersonaCreate`, comprueba que no exista el documento
     (409) y llama a `guardar_foto` (si hay foto).
  6. `db.add(persona)` + `db.flush()` preparan el INSERT sin confirmarlo.
  7. `registrar_transaccion(token, "CREATE", ...)` llama a ms-logs, que valida
     el mismo Bearer y escribe la fila en `transaccion_logs`.
     Si falla -> rollback -> 503. Nunca queda una creación sin auditoría.
  8. `db.commit()` confirma la persona.
  9. Se genera el embedding con Ollama y se guarda en `persona_embeddings`.
     Si Ollama falla, solo se avisa por logger: el CRUD ya terminó bien.
 10. Se responde 201 con los datos de la persona (sin los campos de control).

El patrón se repite en UPDATE y DELETE; en READ no hay flush porque solo se lee.


--------------------------------------------------------------------------------
4. CONVENCIONES QUE NO SE DEBEN ROMPER
--------------------------------------------------------------------------------

- Prefijos de los APIRouter == `location` de gateway/nginx.conf (uno a uno).
- Toda operación (CREATE/READ/UPDATE/DELETE/RAG_QUERY) registra log. Una
  operación nueva sin log está incompleta.
- Reglas de validación IDÉNTICAS en Zod (frontend) y Pydantic (backend).
- Modelos SOLO desde `shared.models`; BD SOLO con `get_db` de `shared.database`.
- Esquema SOLO con Alembic (migración nueva, nunca editar una aplicada).
- La SPA llama solo al gateway; n8n no expone el puerto 5678.
- SECURITY: secretos en variables de entorno; `.env` está en `.gitignore`.
  No imprimir tokens ni claves en logs ni en mensajes de error al usuario.
- Idioma de comentarios, documentación y commits: español. Identificadores en
  los nombres que ya existen (`numero_documento`, `transaccion_logs`, etc.).
